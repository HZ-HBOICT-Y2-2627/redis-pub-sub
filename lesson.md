# Lesson — Redis Streams as a lightweight message queue

This lesson explains how Redis Streams work, why they are a better fit than classic pub/sub for cross-service reliability, and how to build a producer/consumer pipeline from scratch. The cars-auction system is used as the running example throughout.

---

## 1. Why not plain pub/sub?

Redis has had a pub/sub primitive (`PUBLISH` / `SUBSCRIBE`) for a long time. It is dead simple: one client publishes a message to a channel, every subscriber that happens to be connected at that moment receives it.

The word *happens* is the problem. Classic pub/sub is **fire-and-forget**:

- A subscriber that is down, restarting, or slow misses messages permanently.
- There is no replay, no acknowledgement, and no way to know whether anyone received anything.
- You cannot have two competing consumers share the load (fan-out only, no work queues).

For a toy demo this is fine. For cross-service operations that must stay consistent — like deciding whether a car can be deleted while there are active auctions — losing a single message means corrupted data.

**Redis Streams** were added in Redis 5.0 to close this gap. A stream is an append-only log. Every message is persisted (optionally to disk), carries a monotonically increasing ID, and can be replayed at any time. Consumer groups add exactly-once delivery semantics and a fault-tolerance mechanism (the Pending-Entry List).

## 2. Core concepts

### 2.1 The stream

A stream is a Redis key that holds an ordered sequence of entries. Each entry has:

- An **ID** — either auto-generated by Redis (`*`) or supplied by the client. The format is `<milliseconds>-<sequence>`, e.g. `1746700000000-0`.
- A set of **fields** — flat key/value pairs, always stored as strings.

```
events:cars
│
├── 1746700001000-0  type=car.deletion.requested  carId=42  correlationId=abc123  timestamp=...
├── 1746700002000-0  type=car.deletion.requested  carId=99  correlationId=def456  timestamp=...
└── ...
```

### 2.2 XADD — writing to a stream

```bash
XADD events:cars * type car.deletion.requested carId 42 correlationId abc123 timestamp 2026-05-08T10:00:00Z
```

`*` tells Redis to auto-assign the ID. The command returns the assigned ID.

### 2.3 XREAD — reading without a consumer group

The simplest way to read: give a stream name and a starting ID. `0-0` means "from the very beginning"; `$` means "only new messages from now on".

```bash
XREAD COUNT 10 STREAMS events:cars 0-0
```

`XREAD BLOCK <ms>` turns the command into a long-poll: the connection blocks until a new entry arrives or the timeout expires.

```bash
XREAD BLOCK 5000 COUNT 1 STREAMS reply:abc123 0-0
```

This is how **cars-catalog-service** waits for the auction-service to reply during the deletion saga: it blocks for up to 5 seconds on an ephemeral `reply:<correlationId>` stream.

### 2.4 Consumer groups — competing consumers

A **consumer group** is a named cursor attached to a stream. Multiple consumers inside the same group share the work: each message is delivered to exactly one member of the group. Different groups receive every message independently (fan-out between groups, work-queue within a group).

```bash
XGROUP CREATE events:cars auction-service 0 MKSTREAM
```

- `0` — start delivering from the beginning of the stream.
- `MKSTREAM` — create the stream if it does not exist yet.

Reading as part of a group:

```bash
XREADGROUP GROUP auction-service worker-1 BLOCK 5000 COUNT 10 STREAMS events:cars >
```

`>` is the special ID meaning "give me messages not yet delivered to any consumer in this group". Redis moves those messages into the **Pending-Entry List (PEL)**.

### 2.5 XACK — acknowledging messages

A message stays in the PEL until the consumer explicitly acknowledges it. If the consumer crashes before acking, the message remains in the PEL and can be reclaimed later.

```bash
XACK events:cars auction-service 1746700001000-0
```

This is the guarantee: a message is never silently lost. Either it was processed and acked, or it is sitting in the PEL waiting for recovery.

### 2.6 The Pending-Entry List and XAUTOCLAIM

If a consumer crashes mid-handler, its in-flight messages stay in the PEL with a delivery count and idle time. After a configurable visibility timeout, another consumer (or the same one after a restart) can reclaim them:

```bash
XAUTOCLAIM events:cars auction-service recovery-worker 60000 0-0
```

This reclaims all PEL entries idle for more than 60 seconds. A high delivery count is a signal that the message is poisonous — log and move it to a dead-letter stream rather than retrying forever.

## 3. Choreography-based Saga pattern

A **saga** is a sequence of local transactions coordinated across services without a distributed lock. In the **choreography** variant there is no central orchestrator: each service reacts to events and emits its own events in return. Services remain fully decoupled.

The cars-auction system uses a request/reply saga for car deletion:

```text
cars-catalog-service            Redis               auction-service
        │                         │                        │
        │  XADD events:cars       │                        │
        │  car.deletion.requested ├───────────────────────►│
        │                         │                        │ check pending/active auctions
        │                         │                        │
        │◄────────────────────────┤  XADD reply:<uuid>     │
        │  auctions.cancelled_for_car                       │
        │   — or —                │                        │
        │  auctions.cancellation_failed                     │
        │                         │                        │
        │  delete car (on success)│                        │
        │  409 Conflict (on veto) │                        │
```

The reply stream is ephemeral: it is given a 30-second TTL by auction-service and deleted by cars-catalog after reading. This avoids unbounded key growth in Redis.

## 4. Building your own — step by step

### Step 1: Connect to Redis

You need two connections when you mix blocking and non-blocking commands. A blocked `XREAD BLOCK` call ties up the connection; all other commands would queue behind it.

```typescript
import Redis from 'ioredis';

// Regular connection — XADD, XACK, DEL, EXPIRE, etc.
const redis = new Redis(process.env.REDIS_URL!);

// Dedicated blocking connection — XREAD BLOCK, XREADGROUP BLOCK
// maxRetriesPerRequest: null tells ioredis not to time out blocked commands
const redisBlock = new Redis(process.env.REDIS_URL!, { maxRetriesPerRequest: null });
```

See [src/client.ts](src/client.ts) for the factory used in this project.

### Step 2: Define your event shapes

Redis Streams store everything as strings. Define TypeScript interfaces that match the flat key/value structure you will write to the stream.

```typescript
export interface CarDeletionRequestedEvent {
  type: 'car.deletion.requested';
  carId: string;          // numbers serialised as strings
  correlationId: string;  // UUID — links the request to its reply
  timestamp: string;      // ISO-8601
}
```

Provide helpers to convert between objects and the flat `[k, v, k, v, …]` array Redis uses:

```typescript
export function parseFields(fields: string[]): Record<string, string> {
  const result: Record<string, string> = {};
  for (let i = 0; i < fields.length; i += 2) {
    result[fields[i]] = fields[i + 1];
  }
  return result;
}

export function flattenEvent(event: Record<string, string>): string[] {
  return Object.entries(event).flat();
}
```

See [src/events.ts](src/events.ts) for the full definitions.

### Step 3: Publish an event

```typescript
// cars-catalog-service — CarService.deleteCar()
const correlationId = randomUUID();

await redis.xadd(
  'events:cars', '*',
  'type', 'car.deletion.requested',
  'carId', String(id),
  'correlationId', correlationId,
  'timestamp', new Date().toISOString(),
);
```

See [src/publisher.ts](src/publisher.ts) for the generic `publish()` wrapper.

### Step 4: Wait for a reply (request/reply saga)

Block on the ephemeral reply stream. Use `0-0` as the start ID so you catch messages that arrived before the blocking call started (safe because correlation IDs are UUIDs — no collision risk).

```typescript
// cars-catalog-service — CarService.deleteCar() continued
const replyStream = `reply:${correlationId}`;

const result = await (redisBlock as any).xread(
  'BLOCK', '5000',   // wait at most 5 s
  'COUNT', '1',
  'STREAMS', replyStream, '0-0',
) as Array<[string, Array<[string, string[]]>]> | null;

await redis.del(replyStream); // clean up regardless

if (!result) {
  // Timeout — auction-service did not respond; fail open and log
  console.warn(`Saga timeout for car ${id}, proceeding with deletion`);
  await prisma.car.delete({ where: { id } });
  return;
}

const [[, messages]] = result;
const [, fields] = messages[0];
const data = parseFields(fields);

if (data.type === 'auctions.cancelled_for_car') {
  await prisma.car.delete({ where: { id } });
} else if (data.type === 'auctions.cancellation_failed') {
  throw new HttpError(409, data.reason ?? 'Car has active auctions');
}
```

See [../cars-catalog-service/src/services/CarService.ts](../cars-catalog-service/src/services/CarService.ts) for the full implementation.

### Step 5: Set up a consumer group on the receiving service

Create the group once at startup. `MKSTREAM` auto-creates the stream so the producer does not need to run first. `BUSYGROUP` is a normal error when the group already exists — catch and ignore it.

```typescript
// auction-service — startCarEventsConsumer()
try {
  await redis.xgroup('CREATE', 'events:cars', 'auction-service', '0', 'MKSTREAM');
} catch (err: any) {
  if (!err.message?.includes('BUSYGROUP')) throw err;
}
```

### Step 6: Run the consumer loop

```typescript
while (true) {
  try {
    const results = await (redis as any).xreadgroup(
      'GROUP', 'auction-service', 'worker-1',
      'BLOCK', '5000',   // long-poll, returns null on timeout
      'COUNT', '10',
      'STREAMS', 'events:cars', '>',  // > = undelivered messages only
    ) as Array<[string, Array<[string, string[]]>]> | null;

    if (!results) continue;

    for (const [, messages] of results) {
      for (const [id, fields] of messages) {
        const data = parseFields(fields);
        try {
          await handleMessage(data);
          await redis.xack('events:cars', 'auction-service', id); // ack only after success
        } catch (err) {
          console.error(`Handler failed for ${id}:`, err);
          // Message stays in PEL for recovery
        }
      }
    }
  } catch (err: any) {
    if (err.message?.includes('Connection is closed')) break;
    await new Promise(r => setTimeout(r, 1000)); // back-off on unexpected error
  }
}
```

See [../auction-service/src/events/consumer.ts](../auction-service/src/events/consumer.ts) for the full implementation, and [src/consumer.ts](src/consumer.ts) for the reusable `startConsumerLoop()` helper.

### Step 7: Write the reply

```typescript
// auction-service — handleCarDeletionRequested()
const blockers = await prisma.auction.count({
  where: { carId, status: { in: ['pending', 'active'] } },
});

const replyStream = `reply:${correlationId}`;

if (blockers > 0) {
  await redis.xadd(replyStream, '*',
    'type', 'auctions.cancellation_failed',
    'carId', String(carId),
    'correlationId', correlationId,
    'reason', `Car has ${blockers} pending or active auction(s)`,
  );
} else {
  await redis.xadd(replyStream, '*',
    'type', 'auctions.cancelled_for_car',
    'carId', String(carId),
    'correlationId', correlationId,
    'cancelledCount', '0',
  );
}

await redis.expire(replyStream, 30); // self-clean if requester dies
```

## 5. Key design decisions in this codebase

| Decision | Why |
| --- | --- |
| Two Redis connections per service that blocks | A single connection blocked on `XREAD BLOCK` cannot issue any other command. Splitting avoids starvation. |
| `maxRetriesPerRequest: null` on the blocking client | ioredis would otherwise abort blocked commands after a few seconds, thinking they hung. |
| `MKSTREAM` on group creation | Either service can start first; the first XGROUP CREATE creates the stream so the first XADD does not fail. |
| `0-0` start ID in `XREAD BLOCK` | Reads from the beginning so messages that arrive before the blocking call starts are not missed. |
| Ephemeral reply streams with TTL | Avoids unbounded key growth. The requester deletes the key after reading; the TTL is a safety net. |
| Fail-open on saga timeout | If auction-service is down for 5 s the car is deleted with a warning. Infrastructure issues should not permanently block user operations. |
| XACK only after successful handler | If the handler throws, the message stays in the PEL. It can be reclaimed and retried rather than silently dropped. |

## 6. Inspecting streams at runtime

```bash
# All messages in the cars event stream
docker compose exec redis redis-cli XRANGE events:cars - +

# Only the 5 most recent messages
docker compose exec redis redis-cli XREVRANGE events:cars + - COUNT 5

# Check what the auction-service consumer group has not yet processed
docker compose exec redis redis-cli XPENDING events:cars auction-service - + 10

# Check the length of a reply stream (should be 0 or 1 while a saga is in flight)
docker compose exec redis redis-cli XLEN reply:<correlationId>

# Inspect consumer group metadata
docker compose exec redis redis-cli XINFO GROUPS events:cars
```

## 7. What this pattern does NOT cover

- **Dead-letter handling** — messages that fail repeatedly are left in the PEL. A production system should move them to a separate dead-letter stream after N retries and alert an operator.
- **`XAUTOCLAIM` for crashed consumers** — if `worker-1` crashes with messages in its PEL, another process needs to call `XAUTOCLAIM` to reclaim them. This codebase does not implement that yet; it is the natural next step.
- **Stream trimming** — streams grow forever unless trimmed with `XTRIM` or `MAXLEN` on `XADD`. For `events:cars` the volume is low enough that this is not urgent, but a production deployment should add a retention policy.
- **Transactional outbox** — the saga still has a tiny window between writing to the database and publishing the event where the process could crash. An outbox pattern (write event to DB in the same transaction, relay to Redis asynchronously) closes this gap.
